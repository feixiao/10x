# Level 5 通用方案：团队协作版 (Team Edition)

> **适用对象**：3~30 人规模的产研团队、技术部门、技术合伙人组织。
>
> **设计原则**：
> - **工具无关（Tool-Agnostic）**：团队成员可以使用各自偏好的编码 Agent，体系层面不绑定任何一款；
> - **渐进式落地**：不需要推翻现有工作流，在已有的 Git + CI/CD 基础上逐层叠加；
> - **安全与审计优先**：企业级代码资产保护、权限最小化、全链路可追溯。

## 一、 心智模型：团队版 Level 5 与个人版的本质区别

| 维度 | 个人版 | 团队版 |
| :--- | :--- | :--- |
| **信任模型** | 你信任自己的判断力 | 你无法实时盯着每个人的 Agent 在干什么 |
| **防线位置** | 人眼扫一眼 `git diff` | CI/CD 自动化门禁（**人可以漏看，机器不会**） |
| **核心风险** | 自己浪费点 Token | 代码资产外泄、生产事故、测试被偷偷篡改无人知晓 |
| **成本管控** | 自律 | 制度（虚拟 Key 配额、预算上限、审计日志） |

**团队版 Level 5 的核心纲领**：

> 个人版靠**纪律**，团队版靠**制度**。
> 个人版的每一道"人工检查"，在团队版中都必须升级为**自动化的、不可绕过的机器门禁**。

## 三、 六大工程支柱详解

### 支柱 1：统一任务契约规范

**问题**：团队里每个人跟 AI 沟通的方式不一致，有人写一句话描述，有人写三页需求，产出质量参差不齐。

**制度化做法**：

1. **建立团队级任务卡模板**，放在仓库根目录（如 `.ai/template.md`），所有人必须从此模板创建任务：

```markdown
<!-- .ai/template.md — 团队统一任务卡规范 -->
# TASK-{ID}: {标题}

## 关联 Issue / Ticket
{Jira/Linear/GitHub Issue 链接}

## 需求描述
{清晰的行为期望，包含输入输出示例}

## 验收标准
- 验收命令: `{pytest / npm test / go test ...}`
- 覆盖率要求: 新增代码行覆盖率 >= 80%

## 负向清单 (红线)
- [ ] 严禁修改 tests/ 目录下已有的测试文件
- [ ] 严禁修改数据库 migration 文件
- [ ] 严禁引入未经 Tech Lead 批准的新依赖
- [ ] 严禁删除或弱化任何已有断言 (assert)
- [ ] 严禁硬编码密钥、Token 或密码

## 改动范围约束
- 允许修改的目录: {src/auth/, src/middleware/}
- 预估改动行数上限: {200 行}

## 使用的 Agent 工具 (自由选择)
{omp / aider / claude / cursor / 其他}
```

2. **契约卡的创建可以 AI 辅助**但必须人工确认：
   - 可以让 AI 根据 Issue 自动草拟任务卡，但 Tech Lead 必须审查后才能开工。

### 支柱 2：分支策略与物理隔离

**问题**：多人同时用 Agent 写代码，分支冲突频繁。

**制度化做法**：

1. **一任务一分支一 PR**：每个 AI 辅助的任务必须在独立的 `feat/xxx` 或 `fix/xxx` 分支上进行，产出为一个标准 PR；
2. **主干保护**：`main` / `master` 分支设为受保护分支，禁止直接推送，必须通过 PR 合入；
3. **并行隔离**：如果一个开发者同时用 Agent 推进多个任务，建议使用 `git worktree` 隔离（但不强制，分支隔离已经够用）。

**Git 分支规范**（适合写进团队 CONTRIBUTING.md）：

```
main (受保护，仅通过 PR 合入)
  ├── feat/TASK-101-jwt-auth        (张三用 omp 在跑)
  ├── feat/TASK-102-cache-layer     (李四用 aider 在跑)
  ├── fix/TASK-103-login-bug        (王五用 claude 在跑)
  └── feat/TASK-104-export-csv      (赵六手写代码)
```

### 支柱 3：CI/CD 质量门禁（核心防线）

**这是团队版 Level 5 的核心中枢。个人版靠人眼扫 `git diff`，团队版的防线必须是 CI 自动化门禁。**

**门禁 1：回归测试必须全绿**
```yaml
# .github/workflows/ai-quality-gate.yml (GitHub Actions 示例，GitLab CI 类似)
name: AI Quality Gate
on: [pull_request]

jobs:
  regression:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - name: 运行全量回归测试
        run: |
          # 使用项目自带的测试命令（通用，不绑定框架）
          make test  # 或 pytest / npm test / go test ./...
```

**门禁 2：双阶段 Diff 切分审查（防作弊核心）**
```yaml
      - name: 检查 Agent 是否篡改了测试文件
        run: |
          # 获取 PR 改动的文件列表
          CHANGED_FILES=$(git diff --name-only origin/main...HEAD)

          # 检查是否有 tests/ 目录的改动
          TEST_CHANGES=$(echo "$CHANGED_FILES" | grep -E "^tests?/" || true)

          if [ -n "$TEST_CHANGES" ]; then
            echo "::warning::⚠️ 本 PR 修改了以下测试文件，请 Reviewer 重点审查是否存在断言弱化："
            echo "$TEST_CHANGES"
            # 可选：直接阻断合入，要求 Tech Lead 手动批准
            # exit 1
          fi
```

**门禁 3：代码行数异常检测（防 AI 暴力堆砌）**
```yaml
      - name: 检查新增代码量是否异常
        run: |
          ADDITIONS=$(git diff --stat origin/main...HEAD | tail -1 | grep -oE '[0-9]+ insertion' | grep -oE '[0-9]+')
          THRESHOLD=500  # 单 PR 新增超过 500 行触发告警

          if [ "${ADDITIONS:-0}" -gt "$THRESHOLD" ]; then
            echo "::warning::⚠️ 本 PR 新增 ${ADDITIONS} 行代码，超过阈值 ${THRESHOLD} 行。请确认是否为 AI 过度生成。"
          fi
```

**门禁 4：静态分析与 Linter**
```yaml
      - name: 静态分析零新增告警
        run: |
          # 使用项目已有的 linter（通用）
          make lint  # 或 ruff check / eslint / golangci-lint
```

### 支柱 4：确定性编排与熔断保护

**问题**：某个团队成员的 Agent 在后台跑崩了，无限循环烧了一晚上的钱。

**制度化做法**：

1. **团队约定重试上限**：所有人使用 Agent 时，约定连续失败不超过 3 次必须停下来人工介入。
   - 可以通过提供团队级的封装脚本（如前文个人版中的 `run-agent.sh`）来硬编码这个限制。
   - 也可以在 CI 层面限制：单个 Pipeline Job 的超时时间不超过 30 分钟。

2. **失败现场保存**：Agent 搞崩时，开发者应保存报错日志和代码差异（`git diff > debug_snapshot.patch`），方便后续排查和团队知识积累。

3. **可选的调度编排器**：
   - 如果团队有批量跑任务的需求（如一晚上自动修 20 个 Issue），可以引入状态机调度器（本项目的 `scripts/supervisor.py` 或 Temporal / Inngest 等通用编排引擎）。
   - 但对大多数团队而言，**CI/CD 本身就是最好的编排器**——每个 PR 就是一个任务单元，CI 就是自动化校验环节。

### 支柱 5：安全工具层（MCP 或等效权限收敛）

**问题**：Agent 在某个开发者的本地环境里直接连了生产数据库，或者发了一个未经审核的部署命令。

**制度化做法（通用原则，不绑定 MCP 协议）**：

1. **Agent 永远不能直接碰生产环境**：
   - 开发环境和生产环境通过网络隔离（VPN / 安全组）物理分离；
   - Agent 只能访问本地开发库或只读从库（Replica）。

2. **数据库查询白名单化**：
   - 如果 Agent 需要查询数据库排查问题，必须通过受控的中间服务（MCP Server 或等效的 API Wrapper）：
     - 只允许 `SELECT` 和 `EXPLAIN`；
     - 自动注入行数限制（如 `LIMIT 100`）；
     - 禁止 `DROP`, `DELETE`, `UPDATE`, `ALTER`。
   - 实现可以是 MCP Server，也可以是一个简单的 REST API 或 CLI 包装脚本。

3. **生产部署强制人工审批**：
   - CI/CD 流水线中的生产部署阶段必须设置**人工审批门禁（Manual Approval Gate）**；
   - 无论是 GitHub Actions 的 Environment Protection Rules、GitLab 的 Manual Job，还是其他 CI 平台的等效功能。

### 支柱 6：统一模型网关与成本治理

**问题**：团队成员各自注册 API Key，花销不透明，个人 Key 泄露就是安全事故。

**制度化做法**：

1. **禁止个人 API Key 直连模型供应商**：
   - 团队统一通过模型网关（LiteLLM Proxy / Azure API Management / AWS Bedrock Gateway / 云厂商 AI 网关）代理所有请求。
   - 每个团队成员分配一个虚拟 Key（`sk-team-zhangsan-xxx`），不接触真实的供应商密钥。

2. **预算分级管控**：

| 角色 | 月度预算上限 | 可用模型 |
| :--- | :--- | :--- |
| 普通开发者 | $30 / 月 | 快速模型（廉价 / 本地） |
| 高级开发者 | $80 / 月 | 快速模型 + 旗舰模型 |
| Tech Lead | $200 / 月 | 全部模型 |
| CI/CD Pipeline | $100 / 月 | 指定模型（审计专用） |

3. **全量审计日志**：
   - 所有 Prompt 输入、模型输出、Tool Call 参数、Token 消耗、耗时、调用者身份写入持久化存储（PostgreSQL / S3 / 日志平台）；
   - 目的：事后追溯代码产出来源、排查安全事件、优化成本分配。

4. **混合路由（可选但推荐）**：
   - 80% 日常编码走廉价或本地模型；
   - 20% 架构设计、安全审计走云端旗舰模型；
   - 模型网关根据请求标签（如 `x-task-type: coding` vs `x-task-type: architecture`）自动路由。

## 四、 团队角色分工与职责矩阵

| 角色 | 日常职责 | 与 AI 的关系 |
| :--- | :--- | :--- |
| **Tech Lead / 架构师** | 审批架构设计 PR、放行生产发布、处理熔断告警、制定团队 AI 使用规范 | AI 的"老板"：定规则、拍板、兜底 |
| **开发者** | 撰写任务卡、启动 Agent、审查 Diff、提交 PR | AI 的"同事"：委派任务、验收产出 |
| **QA / 安全工程师** | 维护 CI 门禁规则、审查测试改动、运行安全扫描 | AI 的"质检员"：制定检验标准、抽查产出 |
| **平台工程师 / DevOps** | 维护模型网关、管理虚拟 Key 与预算、维护审计日志 | AI 的"后勤部"：保障基础设施 |

## 五、 落地路线图（四周渐进式）

不要一步到位，按以下节奏逐周推进：

### 第 1 周：规范与门禁
| 任务 | 产出 | 负责人 |
| :--- | :--- | :--- |
| 确立团队任务卡模板 | `.ai/template.md` 入库 | Tech Lead |

| CI 加入 Diff 切分检查 | 自动检测 `tests/` 被修改时告警 | DevOps / QA |
| CI 加入代码行数检查 | 新增超 500 行自动告警 | DevOps |

### 第 2 周：安全与隔离
| 任务 | 产出 | 负责人 |
| :--- | :--- | :--- |
| Agent 运行环境与生产环境隔离验证 | 确认 Agent 无法触达生产数据库和服务 | 安全 / DevOps |
| 生产部署环节加入人工审批门禁 | CI/CD 中 prod 阶段需人工确认 | DevOps |
| 制定团队 AI 使用行为准则 | `CONTRIBUTING.md` 更新 AI 使用章节 | Tech Lead |

### 第 3 周：成本与审计
| 任务 | 产出 | 负责人 |
| :--- | :--- | :--- |
| 部署统一模型网关 | 团队级 LiteLLM / 云厂商网关上线 | 平台工程 |
| 为每人分配虚拟 Key 与月度预算 | 配置完成并通知团队 | 平台工程 |
| 开启审计日志 | 可查询任意时段的调用记录 | 平台工程 |

### 第 4 周：优化与迭代
| 任务 | 产出 | 负责人 |
| :--- | :--- | :--- |
| 团队回顾 AI 使用效果（Retro） | 收集痛点、调优门禁阈值 | Tech Lead |
| 建设团队 Skills 知识库（可选） | 将常见编码规范、排查指南沉淀为 Skill 文档 | 全员贡献 |
| 评估混合算力路由效果 | 根据审计日志分析成本分布，调优模型分流 | 平台工程 |

## 六、 团队版自检清单

- [ ] **契约规范**：团队是否有统一的任务卡模板？所有 AI 辅助任务是否都有明确的验收命令和负向清单？
- [ ] **分支保护**：主干分支是否受保护？AI 辅助的代码是否必须通过 PR 合入？
- [ ] **CI 门禁（防作弊）**：CI 是否能自动检测 `tests/` 目录的改动并告警？是否有回归测试全量跑通的硬性要求？
- [ ] **CI 门禁（防堆砌）**：CI 是否有单 PR 代码行数异常检测？是否有 Linter 零新增告警要求？
- [ ] **环境隔离**：开发者的 Agent 是否无法访问生产数据库和生产服务？
- [ ] **部署审批**：生产部署是否有人工审批门禁？是否任何人（包括 Agent）都不能绕过？
- [ ] **密钥安全**：是否所有人通过统一网关访问模型？个人是否不持有供应商原始 API Key？
- [ ] **成本管控**：是否每人有月度 AI 预算上限？超额是否自动阻断？
- [ ] **审计追溯**：是否能查到任意一次 AI 调用的完整 Prompt 和输出？是否能定位到具体人和具体任务？
- [ ] **工具灵活**：团队成员是否可以自由选择 Agent 工具（omp / aider / claude / cursor），而整个质量保障体系完全不受影响？
